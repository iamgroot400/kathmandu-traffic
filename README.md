# Kathmandu Traffic

## What this is trying to prove

We are testing whether Kathmandu's peak-hour arterial congestion can be meaningfully
reduced **without building any new road** — using only two levers a city can actually
deploy: retiming the traffic signals, and charging for road use. Concretely, we build a
mesoscopic simulation of the Ring Road and city-core arterial network (233 nodes, 590
links from OpenStreetMap), load it with a synthetic 260,000-trip peak-hour demand
matrix, and establish a baseline in which 128 intersections run well-tuned fixed-time
signals and drivers reroute within-day onto current travel times (dynamic user optimum,
not a settled equilibrium — day-to-day equilibrium was attempted and does not converge
on this network, see Calibration below). We then measure how much delay can be removed,
relative to that fixed-time baseline, by (a) a queue-actuated adaptive signal heuristic
(hand-coded hysteresis control, not a learned/RL policy) at the 128 signalised
intersections, (b) marginal-cost congestion tolls, and (c) both together — compared
against each other with a paired-seed statistical test, not against a system-optimum
bound (no system-optimum assignment is computed anywhere in this project). The claim is
causal and relative — that these levers recover a specific, quantified share of delay —
**not** a forecast of Kathmandu's actual travel times, because the demand matrix is
synthesised rather than surveyed and the model's absolute numbers pass GEH validation
at only 2 of 6 checked intersections (see Validation below).

## Pipeline

```bash
python scripts/build_od.py          # demand: gravity model over 109 zones
python scripts/build_network.py     # network: OSM -> UXsim, cached as CSV
python scripts/run_baseline.py      # baseline: validate, signalise, simulate
python scripts/find_bottlenecks.py  # rank intersections by delay caused
python scripts/run_due.py           # day-to-day user equilibrium (does not converge - see Calibration)
python scripts/compare.py           # paired-seed sweep across fixed_time/adaptive/pricing/combined
python scripts/run_pricing.py       # measure a toll schedule from an untolled run
python scripts/add_cordon.py        # external demand - tried, made validation worse, not used (D6)
python scripts/validate_hotspots.py # face-validity check against named landmarks
python scripts/geh_check.py         # GEH validation against observed counts
python scripts/sensitivity.py       # +/-20% sensitivity of the baseline's fitted knobs
python scripts/find_bridges.py      # recover OSM bridge tags; flag Ring Road bridges
python scripts/congestion_report.py # per-link density/severity + bridge jam chain-reaction
python scripts/compare_future_demand.py   # 5-year exponential demand projection (paired seeds)
python scripts/compare_capacity_sweep.py  # robustness: H1-H3 across 1200-2400 veh/h/lane
```

## Demand

`data/od_matrix.csv` — `origin_id, dest_id, demand`, generated by `scripts/build_od.py`.
`data/zones.csv` gives each zone's centroid and mass.

| | |
|---|---|
| Zones | 109, on a 1 km grid |
| Zone mass | count of road junctions in the cell |
| Model | gravity, `mass_i × mass_j × exp(−β·d)` |
| β | 0.2 per km |
| Daily trips | 2,600,000 |
| Peak-hour factor (K) | 0.10 |
| **Peak-hour trips** | **260,000** across 10,791 pairs |
| Intrazonal | 4.1% (not loaded onto the network) |

Regenerate, or rescale for a sensitivity run:

```bash
python scripts/build_od.py --cell-km 1.0 --total-trips 260000
python scripts/build_od.py --cell-km 1.0 --total-trips 312000   # +20%
```

Grid size is not a free choice: intrazonal trips have no path through the network,
so they are silently dropped by the simulator. Coarser cells discard more demand —
2 km cells lose 10% of all trips, 1 km loses 4.1%.

### What this demand is not

Junction density is a proxy for activity, not a measurement of it. There is no
land-use data, no survey, and no observed trip counts behind these numbers.
Production and attraction are symmetric, so there is **no peak directionality** —
no net commuter flow into the core in the morning or out in the evening. Treat the
matrix as a hypothesis to test, and re-check any conclusion that depends on its
shape against surveyed counts.

## Baseline

```bash
python scripts/build_network.py     # import OSM into UXsim, cache as CSV (needs network)
python scripts/run_baseline.py      # validate + run the calibrated baseline
```

Network: **233 nodes, 590 links**, 100% strongly connected, zero dead ends.

| Parameter | Value | Why |
|---|---|---|
| Demand | 30% of the 260k peak-hour matrix | arterial share — see below |
| Effective free-flow speed | 30 km/h | OSM's 50 km/h limit is never sustained here |
| Jam density | 0.2 veh/m/lane | ~5 m per vehicle, motorcycle-heavy mix |
| Signals | 128 intersections, 90 s cycle | OSM import creates none |
| Demand window | 3600 s | the peak hour |
| Simulation horizon | 14400 s | 10800 s left some seeds undrained; see Signals below |

Result (15-seed paired sweep, the authoritative figure — see `lab/experiments/E1.md`):
**13.26 km/h** mean speed, **2351 ± 165s** average delay. An earlier single-seed check
at tmax=10800 reported 14.3 km/h / delay ratio 0.79 / 100% completion; that number is
superseded by the 15-seed result above and should not be quoted on its own.

### Signals

UXsim's OSM importer makes every node an unsignalised free merge, so `scripts/signals.py`
adds a two-phase fixed-time plan to each real intersection (3+ approaches on more than
one axis). Opposing arms share a phase; green is split in proportion to the lanes each
phase serves, so the baseline is a *reasonably* timed signal rather than a strawman for
optimisation to beat. 105 nodes stay as free merges — bends, diverges and two-way merges,
where real networks give way rather than signalise.

Signals cost about 3 km/h and raise the delay ratio from 0.65 to 0.79, which is expected:
a two-phase signal halves each approach's capacity. Run `--no-signals` to compare.

Signalising *every* two-approach merge as well (165 nodes) over-constrains the network —
only 78% of trips complete and mean speed falls to 11.5 km/h. Watch for that trap: total
delay appears to *fall*, but only because the delay of the 22% of trips that never
finished goes uncounted.

## Calibration

### Speed friction factor (α = 0.60)

Every link is overridden to **30 km/h** effective free-flow speed, against OSM's
tagged 50 km/h urban arterial limit — a 40% reduction, i.e. α = 0.60. This single
factor stands in for roadside parking, informal bus stops, street vendors, narrow
and encroached lane geometry, and the absence of lane discipline. In a mesoscopic
model these cannot be represented as behaviour (there is no car-following model), so
they enter as a reduced effective speed. The model reproduces their *outcome*; it
cannot test them as a *cause*.

### Fleet composition (PCU = 0.625)

UXsim is single-class — it has no vehicle types, lengths or per-class dynamics. The
fleet mix therefore enters as PCU-weighted demand:

| Class | Share | PCU |
|---|---|---|
| Two-wheelers | 70% | 0.25 |
| Cars / taxis | 20% | 1.00 |
| Micro-buses / buses | 10% | 2.50 |
| **Weighted** | | **0.625** |

Only the *product* `demand_scale × pcu_factor` is identified by the speed calibration,
so the originally fitted 0.30 is decomposed into **0.48 arterial share × 0.625 PCU**.
The simulation is unchanged; the factor is now two parts that can be defended
separately. The 0.2 veh/m/lane jam density is independently consistent with this mix
(mean vehicle length 3.1 m plus a ~2 m gap).

### Route assignment — DUE does not converge

`SolverDUE` **oscillates rather than converging** on this network. Over four
iterations the route-cost gap ran 611.6 → 13.5 → 510.0 → 36.5, with total travel time
swinging roughly 14× between iterations and UXsim warning that 39,355 of 55,900
vehicles failed to finish. The solver replaces adaptive routing with pre-enumerated
fixed routes, which concentrates traffic and gridlocks the network, then over-corrects.

Results therefore use UXsim's default **`homogeneous_DUO`** — within-day rerouting on
current travel times, updated every 600 s — which completes 100% of trips and is
stable. State this in the methodology rather than claiming equilibrium: *route
assignment used within-day dynamic user optimum; day-to-day DUE was attempted but did
not reach a stable gap within a feasible compute budget (~4 min/iteration).*

## Bottlenecks

```bash
python scripts/find_bottlenecks.py --top 20   # writes data/bottlenecks.csv
```

Delay is measured per link and attributed to the link's **downstream** node, since that
is where the queue forms and what a signal can act on. Free-flow travel time is
subtracted, so a link being long or slow does not count as a bottleneck.

Total: **27,361 vehicle-hours** (single-run figure; see caveat below). The top 20 nodes
carry **73%** of it, of which 11 are signalised and therefore controllable. One node,
`3511456911`, carries **22%** of delay in that single run — a three-into-one merge,
already signalised, with a V/C-style ratio of 611.7 (i.e. massively over capacity even
with a working signal; this is a geometry/capacity problem, not a timing one).

**Re-verified 2026-10-18 against 15 seeds at tmax=14400** (`scripts/verify_bottleneck.py`):
the 22% figure was the *high end* of a real distribution, not typical. Across 15 seeds,
this node's share of total delay is **mean 15.7%, range 9.3-21.9%, stdev 3.9%**. It
remains clearly the single largest contributor and the right target for a surgical
capacity fix — just report 15.7% (or "9-22% across seeds"), not 22%, going forward.
Also found in passing: 2 of the 15 seeds showed total network delay 3-5x higher than
the rest (~105,000 vs. a typical 20,000-55,000 veh-h) - not yet investigated, flagged
here so nobody quotes a single-seed total-delay number from this project with false
confidence.

### Why 30% of demand

The network contains only trunk, primary and secondary roads. Trips that stay on
residential and tertiary streets have nowhere to go in this model, so loading the
full citywide matrix puts every trip on a fifth of the city's road length — which
gridlocks (at 100%, only 12% of trips complete and speed collapses to 3 km/h).

The 30% figure is calibrated so mean speed lands in the observed Kathmandu peak
range. **It is a calibration against one aggregate target, not a measured arterial
share** — replace it with surveyed link counts and the GEH check when available.

### What a mesoscopic model cannot tell you

UXsim has no car-following model: no reaction time, no lane discipline, no
overtaking. Vehicles move as platoons along a fundamental diagram. Erratic braking
and poor lane discipline are therefore represented only by their *aggregate effect* —
the reduced free-flow speed above — and the model can reproduce that outcome but
cannot test whether driver behaviour is its cause. That question needs a
microscopic model (SUMO, with reaction time and sublane dynamics).

## Validation against observed counts

```bash
python scripts/geh_check.py   # GEH vs 6 named intersections
```

Checked against JICA/Department of Roads traffic counts (2012 survey; see
`lab/experiments/E6.md`) at 6 named Kathmandu intersections, using the GEH statistic
(the standard model-vs-observed-volume check; GEH < 5 is a conventional pass).

**2 of 6 (33%) pass** — well short of the usual ≥85% target. Thapathali (GEH 0.77)
and Old Baneshwor (GEH 3.16) fit well; Koteshwor (GEH 102, model undershoots by ~5x),
Kalimati, and New Baneshwor also undershoot, while Sorakhutte *overshoots*. The mixed
direction rules out one simple story (e.g. "big junctions are always undershot") and
points instead at the calibration method itself: fitting one global demand scale
against city-wide mean speed constrains total demand, not where it concentrates, so
the model can match the city on average while being wrong — in either direction — at
a specific real intersection.

**What this means for the results above:** the *absolute* delay and speed numbers in
Baseline/Bottlenecks should be read as the model's own internally consistent values,
not as measured Kathmandu quantities. A single-seed spot-check at two of the failing
nodes — Koteshwor (the clearest undershoot) and Sorakhutte (the one node that
overshoots instead) — found the *relative* picture is only
**partly** robust to this gap: pricing and the combined lever reduce delay at both
nodes, in the same direction as the aggregate H2/H3 result, but **adaptive signal
control alone makes Koteshwor's delay 214% worse**, the opposite direction from the
aggregate H1 result (−24.5%) — at exactly the node where the baseline itself
undershoots observed volume by ~5x. This is a real caveat on H1's generalizability,
not just a baseline-calibration footnote: see `lab/experiments/E6.md` for the full
numbers. Validation was not extended to all 233 nodes because the observed-count
sources require manual transcription of scanned survey tables.

**Independent field confirmation:** Tiwari et al. (2024) measured real delay at two
named Ring Road intersections (Satdobato, Gwarko) using the same GEH statistic, and
found signal optimization alone cut delay from 226.5s/201.1s to 51.8s/52.5s per
vehicle — independent, field-measured support for H1's direction, from outside this
project entirely. See the paper's Discussion section.

## Density, bridges, and jam chain-reaction

```bash
python scripts/find_bridges.py      # recover OSM bridge tags, flag Ring Road ones
python scripts/congestion_report.py # per-link density/severity, bridge-to-upstream jam lag
```

UXsim's kinematic-wave links already model density and queue spillback physically -
these scripts surface that at real locations rather than adding a new mechanism.
13 of 71 raw OSM bridge ways resolve to a distinct link in the merged network (2 on
the Ring Road); the rest were absorbed into intersection nodes by the node-merge step
or fall outside the network extract (see `lab/decisions.md` D22). At calibrated
demand, no link reaches "jammed" severity; chain-reaction propagation (a bridge
saturating before its upstream approach does) is measurable but modest.

## What if demand keeps growing?

```bash
python scripts/compare_future_demand.py   # 5-year exponential demand projection
python scripts/compare_capacity_sweep.py  # robustness check across assumed road capacity
```

Projecting forward 5 years at the JICA-reported 16%/year vehicle-registration growth
rate (1991-2011; A12, untested extrapolation) gives 2.1x today's peak-hour demand.
The network does not just get slower - **completion collapses to 36.8%** and mean
speed falls to near zero and stays there, i.e. outright gridlock, with 97 of 590
links (16.4%) reaching "jammed" severity. A separate robustness sweep tests whether
H1-H3's conclusions survive if the model's per-lane capacity assumption (never
directly measured for this network) is lower than calibrated, spanning the
1203-2160 veh/h/lane Tiwari et al. measured in the field; in progress as of this
writing (`lab/notebook/2026-10-19.md`).

## Scope note

The geometry is real; the demand is not. The model has been checked against observed
traffic counts at 6 intersections (see Validation above) and passes at only 2 of 6 -
so results describe the model's own internally consistent behaviour, and the
relative comparisons between control levers more than the absolute numbers, until
broader surveyed counts are available.
